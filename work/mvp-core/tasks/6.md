# Task 6: Voice Handler + Multi-Voice Context

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Orchestrate the full voice-to-tasks pipeline in `src/handlers/voice.js` — the central handler that ties together all services built in previous tasks. This handler is the main business logic entry point: it receives voice messages from grammy, downloads audio via Telegram API, calls the transcription service (faster-whisper), sends the transcript to the task extractor (LLM), formats the numbered task list, sends it to the user with inline rating buttons, and records everything in the database.

A critical part of this task is the per-chat debounce buffer for multi-voice context merging. When a user forwards multiple voice messages at once, Telegram delivers them as separate events. The handler must collect all voices arriving within a 3-second window per chat, then process the entire batch as a single context — concatenating transcripts before sending to the LLM. This produces one unified task list from multiple voice messages.

The handler must also implement partial failure handling for multi-voice batches: if one voice in a batch fails transcription, the remaining voices are still processed and the user is notified about the failure (Decision 19). The trial counter increments only for successfully processed voices.

After sending the task list, the handler sets session state for the feedback flow (handled by Task 7's feedback handler) and resets any pending feedback session if the user sends a new voice while feedback is in progress (Decision 9: silent abandon).

## What to do

1. Create `src/handlers/voice.js` exporting a voice message handler function compatible with grammy's `bot.on('message:voice')` and `bot.on('message:audio')` patterns.

2. Implement the per-chat debounce buffer:
   - Use a module-level `Map<chatId, { voices: [], timer }>` to collect voices per chat.
   - On first voice in a chat: start a 3-second timer, add voice to buffer.
   - On subsequent voices within the window: clear existing timer, add voice, start new 3-second timer.
   - When timer fires: process the collected batch, clear the buffer entry.
   - Enforce batch limit of 10 voices per buffer (Decision 10). If exceeded, notify user and process only the first 10.

3. Implement the voice processing pipeline (runs after debounce timer fires):
   - Check user trial status via `getUserByTelegramId` / `upsertUser`. If trial exhausted (trial_remaining === 0), do not process — trigger survey/block flow as appropriate.
   - If user has pending feedback session (awaitingFeedback, awaitingComment, awaitingConsent), silently reset session state (Decision 9).
   - For each voice in the batch: download audio file via grammy's `ctx.api.getFile()` + fetch, then call `transcribe()` from transcription service. Wrap each in try/catch for partial failure handling.
   - Concatenate successful transcripts (separator: newline). Track failed count.
   - If all voices failed: send error message to user, do not increment counter. Return.
   - Truncate combined transcript to 4000 chars if needed; set a truncation flag (Decision 4).
   - Call `extractTasks()` from task extractor service with the combined transcript.
   - If result indicates no tasks found: send "no tasks" message.
   - If result indicates too many tasks (>10): send "split" message (Decision 10).
   - Format the numbered task list using formatting functions from `src/utils/messages.js`.
   - Send the formatted task list to user. If truncation occurred, append a note.
   - If partial failures occurred, append a note about how many voices failed (Decision 19).
   - Send inline keyboard with rating buttons 1-5 below the task list.

4. After successful task list delivery:
   - Create voice_request records in DB for each successfully processed voice via `createVoiceRequest()`.
   - Update voice_request records with task_count and transcript_length via `updateVoiceRequest()`.
   - Decrement trial counter once via `decrementTrial()` (counter increments only on successful delivery).
   - Set session state: `awaitingFeedback = true`, `voiceRequestId = <id>` (for feedback handler in Task 7).

5. Export the debounce buffer map (or a `clearBuffer` function) for testability.

**Dependencies:**

- `node-fetch` — for downloading audio files from Telegram

**Edge cases:**
- Voice arrives exactly as debounce timer fires — treat as new buffer (timer already cleared)
- User sends 11+ voices — cap at 10, notify about the limit, process the first 10
- Combined transcript from multiple voices exceeds 4000 chars — truncate with notification
- Transcription timeout (20s per Decision 14) — catch as partial failure
- LLM extraction failure — send friendly error message, do not increment counter
- No tasks found in transcript — send explicit friendly message (not empty list)
- Too many tasks (>10) — send "split into shorter messages" prompt (Decision 10)
- User in trial_phase=3 (exhausted) — reject with appropriate message
- User in survey flow (inSurvey=true) — let survey handler deal with it, or reject voice with "finish survey first"
- Audio file download failure from Telegram — treat as failed voice in batch

**Implementation hints:**
- Use `ctx.api.getFile(fileId)` to get file path, then fetch `https://api.telegram.org/file/bot<token>/<file_path>` to download.
- grammy's `InlineKeyboard` class for rating buttons: `.text("1", "rate:1").text("2", "rate:2")...`
- `setTimeout` / `clearTimeout` for debounce. Use the native timer functions. For tests, use Jest fake timers (`jest.useFakeTimers()`).
- The debounce Map key should be `ctx.chat.id` (number).
- When resetting feedback session (Decision 9), clear: `awaitingFeedback`, `awaitingComment`, `awaitingConsent`, `voiceRequestId`.
- Log request metadata: userId, chatId, voiceCount, totalDuration, taskCount, processingTimeMs. Never log transcript text or audio content (Decision 12).
