# Tech Spec: Voice Action Buttons — transcribe → choose (tasks or summary)

## Context

Currently the voice pipeline auto-extracts tasks after transcription. The user has no choice — they always get a task list. This works for task-oriented voices but fails for non-task voices (status updates, observations, agreements).

**Reference implementation:** The same mechanic was successfully deployed in МаркетБот (Python/aiogram): after transcription, show the transcript with an inline button "Сделать резюме" that triggers summarization on click. We replicate this pattern and add task extraction as a parallel button choice.

## What we're changing

**Before (current):**
```
voice → transcribe → extract tasks → numbered list → rating 1-5
```

**After:**
```
voice → transcribe → show transcript + buttons [📋 Извлечь задачи] [📝 Сделать резюме]
   ↓ (user clicks)
   ├─ 📋 Извлечь задачи → LLM extract tasks → numbered list → rating 1-5
   └─ 📝 Сделать резюме → LLM summarize → first-person summary → done (no rating)
```

The debounce buffer, transcription service, trial system, and feedback flow for task extraction remain unchanged. The summary flow is a new, lightweight path with no rating (summary is informational, not an artifact).

## Architecture

### Session state additions

New field `awaitingAction` tracks which button the user is expected to click:

```js
{
  awaitingAction: false,      // waiting for task/summary button press
  pendingAction: null,        // 'tasks' or 'summary' — which button was clicked
  transcript: null,           // stored transcript for callback handler
  // existing fields:
  awaitingFeedback: false,
  voiceRequestId: null,
  awaitingComment: false,
  awaitingConsent: false,
  inSurvey: false,
  surveyRetries: {},
}
```

### New callback handlers

Two new callback patterns registered in `feedback.js` (already the central callback router):

| Callback data | Handler | What it does |
|---------------|---------|-------------|
| `action:tasks` | `handleActionTasks()` | Runs current task extraction flow |
| `action:summary` | `handleActionSummary()` | New: LLM summary of voice content |

### Summary flow

The summary is generated by calling GigaChat with a system prompt that asks it to produce a concise, first-person summary of the voice transcript. Unlike МаркетБот's `summarize_voice_message()` which loads project context, ToTalk-ToDo has no project context — the summary is self-contained.

**System prompt** (inline, no separate file for MVP):
```
Ты делаешь краткое резюме голосового сообщения.
Пиши от первого лица, как если бы говорящий сам сформулировал свои мысли.
Убери словесный мусор, повторы, ложные старты.
Выведи 2-5 ключевых пунктов в виде маркированного списка.
Если голосовое было о задачах — упомяни их кратко.
Если это статус или наблюдение — передай суть.
Не выдумывай факты, которых не было в транскрипте.
```

### Flow details

**Step 1 — Voice arrives** (unchanged until transcription):
1. Voice → debounce buffer → transcription → same as before
2. After transcription: show transcript + action buttons (inline keyboard)
3. Store transcript + action state in session
4. Log transcription metadata

**Step 2 — User clicks 📋 Извлечь задачи**:
1. Clear action buttons (`editReplyMarkup`)
2. Run current task extraction pipeline (unchanged logic)
3. Send numbered task list + rating 1-5 buttons
4. Set `awaitingFeedback = true`, `voiceRequestId = ...`

**Step 3 — User clicks 📝 Сделать резюме**:
1. Clear action buttons
2. Call LLM with summary system prompt + transcript
3. Send summary with brief "Готово" message
4. Set `voiceRequestId` (for analytics) but NO rating flow
5. Decrement trial counter (still counts as a processing)
6. Log action

**Step 4 — Voice during pending action**:
Per Decision 9 (feedback interruption), if a new voice arrives while action buttons are pending, silently abandon and process the new voice. Same pattern as current feedback abandonment.

### Key decisions

#### Decision 1: Summary has no rating flow
**Decision:** After summary is shown, no 1-5 rating buttons. Just a "Готово" confirmation.
**Rationale:** Summary is informational, not an artifact. Rating is for task extraction quality. Adding rating to summary adds friction without useful signal for MVP.
**Alternatives considered:** Rating on both (more data but more friction), rating only on summary (defeats task extraction feedback)

#### Decision 2: Transcript shown inline, not as separate message
**Decision:** Single message: "🗣 Распознано: {transcript}" followed by "Что сделать с расшифровкой?" with two buttons. Status message deleted before buttons appear.
**Rationale:** Minimizes message clutter. МаркетБот uses the same pattern.
**Alternatives considered:** Separate messages (more visible but noisier)

#### Decision 3: Summary LLM call uses same provider (GigaChat)
**Decision:** No new provider. GigaChat handles both task extraction and summary via different system prompts.
**Rationale:** Already configured, free tier sufficient. Summary is short (~100-300 tokens).
**Alternatives considered:** Separate cheaper model for summary (overengineering for MVP)

#### Decision 4: Summary prompt is inline (no file)
**Decision:** Summary system prompt is a string constant in code, not a separate file.
**Rationale:** Task extraction prompt needs iteration without code changes (core feature). Summary prompt is stable and simple — unlikely to change in MVP.
**Alternatives considered:** Separate file (consistent with task extraction but unnecessary complexity)

#### Decision 5: Trial counter decremented on both actions
**Decision:** Both "Извлечь задачи" and "Сделать резюме" consume one trial credit.
**Rationale:** Both use LLM API calls and compute resources. Fair accounting.
**Alternatives considered:** Free summaries (could be abused), half-credit for summary (complex for MVP)

#### Decision 6: Action buttons have no explicit TTL
**Decision:** Action buttons persist in chat until clicked or replaced by a new voice message. Session state is cleared on new voice (Decision 9 pattern).
**Rationale:** Telegram inline keyboards don't auto-expire. Adding TTL requires background cleanup (overengineering for MVP with 5 testers).
**Alternatives considered:** 5-minute TTL with auto-delete (cleaner but complex)

### Risks

| Risk | Mitigation |
|------|-----------|
| GigaChat summary quality | Prompt is simple, can iterate inline. Swap provider if needed (existing abstraction) |
| Two buttons clutter on mobile | Labels are short emoji + text. Test on real device before deploy |
| Trial change (20→10) breaks existing users | Migration only applies to new users; existing `trial_remaining` values preserved |
| Session state grows | 3 new boolean/string fields. Negligible for grammy in-memory session |

## Testing Strategy

### Unit tests (new)
- Action button callback handlers: test `action:tasks` triggers extraction, `action:summary` triggers summary
- Summary LLM call: mock provider, verify prompt passed correctly, verify response formatted
- Trial numbers: verify default 20, survey bonus +10, block at 0
- Session state: verify `awaitingAction` set after transcription, cleared on button click
- Voice during pending action: verify transcript/action abandoned, new voice processed

### Integration tests (updated)
- Full pipeline with action choice: voice → transcript → click tasks → task list → rating
- Summary flow: voice → transcript → click summary → summary text → no rating
- Trial system with new numbers: 20 → survey → +10 → block

### E2E (manual, 3 scenarios)
1. Voice → click 📋 → task list → rate 5 (existing flow, now via button)
2. Voice → click 📝 → summary → no rating
3. Voice → send new voice before clicking button → old buttons ignored, new voice processed

## Acceptance Criteria

- [ ] After transcription, user sees transcript + inline keyboard with [📋 Извлечь задачи] [📝 Сделать резюме]
- [ ] Click 📋 → task list with rating buttons (existing flow preserved)
- [ ] Click 📝 → concise summary, no rating buttons
- [ ] New voice during pending action → old action abandoned
- [ ] Trial counter: starts at 20, survey gives +10, block at 0
- [ ] Both actions decrement trial counter
- [ ] All unit tests pass
- [ ] Integration tests pass (updated)
- [ ] DB migration `002_trial_numbers.sql` runs on fresh and existing DB
- [ ] No regression: existing voice→task→rating flow works end-to-end
